# 设计说明

本文件记录主要设计决策。它会随项目演进修改（与只追加的 `DEVLOG.md` 不同）。

## 1. LLM 决定什么，什么保持确定性

| 环节 | 由谁负责 | 原因 |
|---|---|---|
| 来源 / 日期校验、去重 | 代码 | 规则明确，必须 100% 一致 |
| 单件成本、利润、回本点、敏感度 | 代码（`economics/`） | 可复现、可审计；UI 与 Agent 调用同一函数 |
| 证据是否过期 | 代码 + 品类配置的保鲜期 | 同上 |
| 引用是否真实存在于原文 | 代码（第 1 阶段 `add_claim` 校验） | 防编造的硬约束，不能靠提示词 |
| 编排流程、轮数上限、预算 | 代码（状态机） | 可预测、可中断、可重放 |
| 评论打标签、痛点归并 | LLM（便宜模型、批量） | 语义理解，结果可人工修正 |
| 提出痛点 / 空缺 / 风险论断 | LLM Agent | 需要综合判断，但必须带引用 |
| 质疑论断 | LLM Agent（独立提示词） | 专门寻找反例和证据不足 |
| 综合与下一步调查 | LLM 协调 Agent | 必须对每条未解决质疑表态（代码检查覆盖率） |
| 有现实影响的动作 | **人** | Agent 只能提议，见第 4 节 |

原则：**LLM 负责判断，代码负责事实与约束。** Agent 只能通过工具读写数据库，不能直接产出最终报告。

## 2. 失败的检测与恢复

- 每次调查是一条 `research_run`，记录模型、提示词版本、状态、错误和 token 用量。
- 每次工具调用是一条 `agent_step`，记录输入输出、是否成功、错误原因（如「引用的原文不存在」）和耗时。
- 可检测的失败类型（第 1 阶段实现）：引用校验被拒、结构化输出不合格、质疑未被回应、超出轮数或预算、API 错误。
- 恢复：被拒的工具调用把原因返回给 Agent 让它重试；超限时运行暂停为 `paused`，并生成需要人工处理的待办，而不是带着不完整的结论继续。
- 真实发生的问题会记录到 `DEVLOG.md`，包括现象、如何发现、如何修复。

## 3. 用评估决定改动能否上线（第 1 阶段）

- 固定评估集，覆盖几类场景：痛点已被竞品解决（应输出「暂不进入」）、成本不成立、证据确实充分、证据不足（应如实说「不知道」）。
- 指标：引用有效率、编造拦截率、结论与预期是否一致、单次调查成本。
- 规则：修改提示词或模型后必须重跑评估集；引用有效率或预期结论命中率下降则不合入。结果连同 `prompt_version` 一起记录。
- 确定性部分（成本引擎、导入）用普通单元测试覆盖。

## 4. 人工审批与防重复执行

- 需要人工批准的动作：改变机会阶段、联系供应商、下单拿样、任何花钱或对外发送的操作。
- Agent 只能写入 `action_proposal`（状态为 proposed），由人批准后才执行。
- `idempotency_key` 唯一约束：重试的 Agent 再次提出同一动作不会产生第二条；执行前检查状态，已执行的不会再执行。
- 数据导入同样幂等：证据按规范化文本的哈希去重，同一文件导入两次结果不变。

## 5. 长期记忆：保留几个月的上下文，但不用过期或冲突的信息

- 记忆就是数据库本身，不是一段不断增长的对话摘要。
- 每条证据都有采集日期；品类配置为不同类型的证据设定保鲜期（如商品页面 30 天、报价 60 天），过期证据会被标出，需要重新采集。
- 更新不覆盖旧数据：新证据通过 `superseded_by_id` 取代旧证据，历史保留（例如可以看到报价如何变化），但旧证据不再作为当前事实使用。
- 冲突不被静默合并：证据之间的矛盾会成为 `contradiction` 类型的质疑，必须有明确的处理结论。
- 决策会保存当时的假设快照，之后的验证结果可以回填，判断哪些假设被证实或推翻。

## 6. 面对新用户 / 新品类，第一周交付什么

- 第 1–2 天：建立品类配置，导入 10–20 个竞品及其评论、2–3 份报价。
- 第 3–4 天：跑成本情景和敏感度分析，找出最关键的那个假设。
- 第 5 天：一份带引用的机会评估，加上一个具体的小规模验证计划。
- 成功指标：从开始到第一个有依据的决策所用的时间；结论中带有效引用的比例；用户需要手动修正的比例；最终验证结果是否与预测方向一致。

## 7. Agent 工具层与权限（第 1.1 步）

Agent 只能通过工具读写数据。每次调用都会依次经过执行器（`agents/executor.py`）的这几步：
工具存在 → Agent 有权限 → 调用次数预算未用完 → 参数符合 schema → 在 SAVEPOINT 中执行（失败就回滚）→ 写入 `agent_step`。
失败不会抛异常，而是返回 `{ok: false, error_type, error}`，交给模型自我修正。

| Agent | 读 | 写 |
|---|---|---|
| demand（需求） | 搜索 / 读取证据、竞品、痛点统计 | 论断（pain / other） |
| competitor（竞品） | 同上 | 论断（gap / risk / other） |
| cost（成本） | 同上 + 报价、成本计算 | 论断（cost / risk） |
| challenger（质疑） | 同上 + 报价、成本计算、论断列表 | 质疑（**不能写论断**） |
| coordinator（协调） | 读取 + 论断列表 | 处理质疑、记录决策、提议动作 |

代码强制的规则：
- 有未处理的质疑时，不能记录决策。
- 反驳质疑必须引用证据，且引用要通过原文校验。
- "进入"的决策必须有验证计划，并且依据的论断全部是 supported。
- 质疑被接受后，论断状态自动降级：反例、矛盾、逻辑跳跃 → refuted；证据不足 → unverified。
- 同一条质疑、同一个动作重复提交时幂等，不会产生重复记录。
- 搜索结果默认排除已被取代的证据，并标出过期证据。

全文检索索引是派生数据，不属于表结构：每次初始化数据库时检查一遍，缺了就重建。这样即使以后的迁移重建了 evidence 表，索引的同步触发器也不会悄悄失效。
